# 2026-05-11 详情页 Workflow 与整体架构整理

## 1. 今天详情页这条线，核心在做什么

今天围绕 `admin-detail` 这类后台详情页，系统已经形成了一条比较完整的生成链路，重点不是“直接把一句话丢给 LLM”，而是先把需求结构化，再去做知识召回和代码生成。

可以先把目标理解成三件事：

1. 先识别“这是不是一个后台详情页”。
2. 再拆出“详情页里必须有哪些区块和状态语义”。
3. 最后把这些结构化信息送给知识库和 Prompt，约束最终生成结果。

详情页这条线目前最关键的优化点有两个：

- **页型识别更明确**：避免把“审核详情页”误生成为列表页或 CRUD 表格页。
- **状态驱动更前置**：把状态、按钮、权限、流转放进 `workflow` 推理，而不是让模型零散硬编码。

## 2. 详情页完整 Workflow

### 2.1 请求入口

前端通过 `POST /api/generate` 发起请求：

- 前端请求：`packages/web/src/lib/api.ts`
- 控制器入口：`packages/server/src/controllers/generate.controller.ts`
- 主服务入口：`packages/server/src/services/generate.service.ts`

主链路可以概括为：

```text
PromptInput
  -> useGenerate.generate()
  -> POST /api/generate
  -> generateController
  -> generateService
      -> decomposeRequirement
      -> retrieveKnowledgeForDecomposition
      -> retrieveKnowledgeForSections
      -> buildGenerationPlan
      -> buildPrompt
      -> callLLM
      -> safeJsonParse + schema parse
  -> 前端 ResultPanel 展示结果
```

### 2.2 第一步：需求拆分

`generateService()` 的第一步就是：

```ts
const decomposition = decomposeRequirement(input);
```

这里做的是规则式预处理，入口在：

- `packages/server/src/services/requirement-decomposition.service.ts`

它会完成几件事：

1. 规范化用户输入。
2. 匹配页面类型 `pageType`。
3. 识别命中的子任务 `subtasks`。
4. 基于 profile 生成推荐区块 `sections`。
5. 如命中状态词，则透传页型自带的 `workflow`。

### 2.3 第二步：识别为 `admin-detail`

详情页识别逻辑定义在：

- `packages/server/src/services/requirement-decomposition/page-profiles/admin-detail.ts`

当前 `admin-detail` 的判断大意是：

- 需求里有明显详情语义，如“详情页 / 审核详情 / 审批详情 / 用户详情”；
- 同时有后台语境，如“后台 / 审核 / 审批 / 权限”；
- 不能更像新增页；
- 也不能更像管理列表页。

这一步的价值很大，因为它直接决定后面整条链路的“默认理解方式”。

### 2.4 第三步：拆成详情页子任务

`admin-detail` 当前主要拆成这些子任务：

- `detail-header`：详情页头部
- `base-info`：基础信息区
- `content-detail`：内容详情区
- `audit-records`：审核记录
- `operation-log`：操作日志
- `timeline`：日志时间线

其中优先级大致是：

- `must`：头部、基础信息、审核记录
- `should`：内容详情、操作日志、时间线

这意味着系统不是只知道“这是个详情页”，而是已经知道“详情页至少要长成什么样”。

### 2.5 第四步：从子任务生成结构区块

区块生成在：

- `packages/server/src/services/requirement-decomposition/build-sections.ts`

`admin-detail` 会进一步落成这几个结构区块：

- `page-header`
- `base-info`
- `content-detail`
- `audit-records`
- `operation-log`
- `timeline`

其中：

- `page-header` / `base-info` / `audit-records` 是必带骨架；
- 其余区块按命中的子任务决定是否带出。

这一步很关键，因为系统开始从“语义任务”过渡到“页面骨架”。

### 2.6 第五步：workflow 介入状态推理

详情页的 `workflow` 也定义在 `admin-detail.ts` 中，目前是一份默认状态机：

- 当前默认状态：`草稿`
- 流转关系：
  - `草稿 -> 待审核`
  - `待审核 -> 处理中 / 已通过 / 已拒绝`
  - `处理中 -> 已通过 / 已拒绝`
  - `已拒绝 -> 草稿`
  - `已通过 -> 无后续流转`

这里最重要的设计原则是：

- `workflow` **不是 section**
- `workflow` **不单独生成一个状态模块**
- `workflow` 只负责给 LLM 一个“状态、权限、按钮如何推理”的统一参考

也就是说，它影响的是：

- Header 上的状态 Tag
- 操作按钮区
- 按钮可见性 / 禁用态
- 某些内容区块在不同状态下的呈现方式

而不是强行拆出一个独立的“workflow 面板”。

### 2.7 第六步：知识召回

当 `decomposition.enabled` 为真时，系统不会只拿原始输入去检索，而是走：

- `retrieveKnowledgeForDecomposition()`
- `retrieveKnowledgeForSections()`

对应文件：

- `packages/server/src/services/component-knowledge.service.ts`

这里会把以下内容一起转成查询：

- 原始需求
- 需求摘要
- 每个子任务的关键词
- 每个 section 的结构提示
- `workflow` 抽出的状态词

所以详情页现在的召回，不再只是搜“详情页”三个字，而是会搜：

- 详情页头部
- 状态标签
- 基础信息
- 审核记录
- 操作日志
- 时间线
- 状态驱动 UI

这也是最近详情页命中 `ZhDetailHeader`、`ZhBaseInfo` 这类组件更稳定的原因。

### 2.8 第七步：生成规划

在知识召回之后，系统会做一层生成规划：

- `packages/server/src/services/generation-plan.service.ts`
- `packages/server/src/services/generation-plan/section-component-policy.ts`

这一层会把每个 section 变成更面向代码生成的施工图，包括：

- 这个区块的目标是什么
- 推荐哪些组件
- 为什么推荐这些组件
- 可以参考哪些 snippet

对详情页来说，比较关键的映射包括：

- `page-header` -> `ZhDetailHeader` / `ZhButton`
- `base-info` -> `ZhBaseInfo` / `ZhBaseItem` / `ZhGrid`
- `audit-records` -> `ZhBaseInfo` / `ZhDetailSubTitle`

这让 Prompt 不再只是“给模型一堆资料”，而是“给模型一个结构化施工方案”。

### 2.9 第八步：Prompt 约束最终生成

Prompt 构造在：

- `packages/server/src/services/prompt.service.ts`

这里会把详情页专属要求显式写给模型，例如：

- Header 必须包含标题、状态 Tag、操作按钮区
- 当前状态优先从 `workflow.current` 推理
- 状态文案、颜色、按钮集合要从集中映射推导
- 不要把详情页生成为列表页或 CRUD 表格页
- 主体优先组织成基础信息、内容详情、审核记录、操作日志/时间线

这一层相当于给模型“最后一道扶手”。

## 3. workflow 在详情页里的真实职责

这个点今天特别值得单独记一下，因为它很容易被误解。

### 3.1 workflow 不是页面区块

`workflow` 不是页面上一个实体模块，而是一份跨区块状态机模板。它的职责是帮助 LLM 推理：

- 当前状态是什么
- 当前状态允许哪些动作
- 不同动作受什么权限影响
- 页面哪些区域要随状态变化

### 3.2 workflow 更像“页面行为骨架”

如果用工程视角看，它更接近下面这类前端组织方式：

```ts
const currentStatus = detail.workflow?.current ?? detail.status;
const statusConfig = { ... };
const actionMap = { ... };
```

然后页面头部、按钮区、记录区都从这套集中配置取值。

所以 `workflow` 的本质不是“多一个展示区”，而是“统一状态驱动源”。

### 3.3 workflow 解决的核心问题

它主要在解决三个常见问题：

1. 模型把状态文案、Tag 颜色、按钮集合写死在模板分支里。
2. Header 状态和操作区逻辑分散，不可维护。
3. 详情页虽然有状态流转，但生成结果看起来像静态展示页。

## 4. 当前整体架构，可以怎么理解

这个项目现在已经比较清楚地分成了前端展示层和后端生成层。

### 4.1 前端层

位置：

- `packages/web`

前端职责比较纯：

- 收集用户输入
- 调用 `/api/generate`
- 维护加载、成功、失败状态
- 渲染组件建议、解释和代码结果

核心文件：

- `packages/web/src/App.vue`
- `packages/web/src/composables/useGenerate.ts`
- `packages/web/src/lib/api.ts`

前端目前不承担“页型识别”“知识召回”“Prompt 拼装”这些复杂逻辑，它更像一个干净的生成工作台。

### 4.2 后端接口层

位置：

- `packages/server/src/controllers`
- `packages/server/src/routes`

职责：

- 接收请求
- 校验输入
- 返回统一 JSON 结果

这里保持得比较薄，核心逻辑都下沉到 service。

### 4.3 后端领域服务层

位置：

- `packages/server/src/services`

这一层是项目真正的核心。当前可以理解成 5 个子层：

1. `requirement-decomposition`
   负责页型识别、子任务拆分、section 骨架、workflow 透传。

2. `component-knowledge`
   负责组件知识库检索、关键词扩展、卡片/chunk 召回与排序。

3. `generation-plan`
   负责把 decomposition 和 knowledge 进一步整理成“页面施工图”。

4. `prompt`
   负责把规则、规划、知识整合成最终 Prompt。

5. `llm`
   负责真正调用模型，拿回原始生成结果。

### 4.4 一句话总结当前后端架构

可以把当前后端理解为：

**规则预处理层 -> 知识召回层 -> 生成规划层 -> Prompt 编排层 -> LLM 执行层**

这个分层的好处是：

- 比纯 Prompt 方案更可控
- 比纯规则方案更灵活
- 后续加新页型时，只需要补 profile、section policy 和 prompt 约束，不用推翻整条链路

## 5. 今天这套设计最重要的几个共识

### 5.1 `admin-detail` 的核心不是“展示字段”

它的真正核心是：

- 状态
- 权限
- 操作
- 记录

也就是一个带业务流转语义的详情页，而不是简单静态详情卡片。

### 5.2 详情页生成质量，取决于三层是否同时成立

要想生成结果稳定，至少要同时成立：

1. 页型识别正确，先命中 `admin-detail`
2. 知识召回正确，能召回头部/基础信息/记录类组件
3. Prompt 约束正确，明确禁止退化成 CRUD 列表页

任何一层弱掉，详情页都会跑偏。

### 5.3 workflow 应该继续保持“轻状态机、重推理”

当前 `workflow` 只保留：

- `current`
- `transitions`

这个设计是对的。它保持了配置层足够轻，但把最终状态 UI 推理留给 Prompt 和 LLM 去完成，扩展成本低，也不容易把配置做成另一套难维护的 DSL。

---

## 6. 后续可以继续补强的点

如果后面继续做详情页，这几个方向会比较值：

- 把 `admin-detail` 的 `workflow` 从“默认模板”继续扩成“可按业务注入”的状态机来源。
- 在 `generation-plan` 层增加“状态驱动组件策略”，让 Header / 按钮区的推荐更稳定。
- 为 `admin-detail` 增加更强的回归测试，覆盖“头部状态 + 审核记录 + 日志时间线”组合场景。
- 进一步区分“业务审核记录”和“系统操作日志”的召回与展示策略，避免两者混用。

---

## 7. 最后一句话版本

今天详情页这条线，本质上是在把“后台详情页”从一个模糊自然语言需求，变成一套可控的结构化生成流程：

**先识别页型，再拆结构，再用 workflow 驱动状态语义，再结合知识库和生成规划去约束 LLM 输出。**
